# Learnings — TAT-3312

- **Investigation was fast (~clear), fix was one line.** Reading `usePerpsOrderForm` + `amount-input.tsx` + the `isInsufficientFunds` check in `perps-order-entry-page.tsx` made the rounding boundary obvious. Reading mobile's `usePerpsOrderForm` (`Math.floor`) confirmed the intended behavior and the right layer for the fix.
- **Deterministic repro came from reading the live balance.** The bug only triggers when `availableBalance * leverage` has a 3rd decimal ≥ 5. Reading `stateHooks.getPerpsStreamManager().account.cache.withdrawableBalance` (= 21.3816765) showed default leverage 3 reproduces it (64.1450295 → 64.15). No guessing.
- **Biggest time sink: the frozen-slot rebuild + reload.** After editing source, the first `refresh-build.sh` crashed with an internal webpack error (`HarmonyImportSpecifierDependency ... buildMeta`) — transient, succeeded on retry. Then a plain `Page.navigate` reload kept serving the **cached old bundle** (amount still 64.15); only a full extension reload (`stateHooks.reloadExtension()` then `reopen-browser.sh`) loaded the new dist. Lesson: after a frozen rebuild, do a full extension reopen, not just a page reload.
- **Hydration race on fresh navigation.** Right after a reload, the order form's reset effect (driven by stream churn / `initialLeverage` config load) wipes a programmatically-set amount. On a cleanly reopened, settled browser the value sticks. The recipe passes reliably once the browser is stable.
- **Submit button testID is `submit-order-button`** (the page-level button in `perps-order-entry-page.tsx`), not `order-entry-submit-button` (the one in `order-entry.tsx`, which renders in a different mode). Worth knowing for future perps order-entry recipes.
